# Подготовка к защите SaleScout Price Bot

## Короткое объяснение проекта

«Я сделал мини-версию прайс-бота. Она получает товары с текущей ценой, допустимыми границами, шагом и предложениями конкурентов. Сервер рассчитывает рекомендуемые цены, а страница показывает старую и новую цену, разницу и причину. Правила реализованы в чистой функции, HTTP-граница валидирует данные, интерфейс обращается к серверу через fetch. Расчёт проверен на официальных примерах и пограничных случаях».

Не говорите, что проект отслеживает реальный Kaspi или применяет цены в магазине: здесь демонстрационные данные, а результат — рекомендация.

## Как проходит запрос

1. `frontend/App.tsx` получает начальные товары из `data/products.json`.
2. Нажатие кнопки запускает `calculate()`: включается загрузка, очищаются прошлый результат и ошибка.
3. `frontend/api.ts` отправляет `fetch('/reprice', ...)`: метод POST, JSON-массив и заголовок `Content-Type`.
4. Vite proxy пересылает запрос с frontend-порта на Express. Для браузера запрос остаётся на том же origin.
5. `express.json()` разбирает JSON. `parseProducts()` проверяет данные во время выполнения.
6. Обработчик вызывает `parsed.products.map(calculatePrice)` и возвращает JSON.
7. Клиент проверяет HTTP-статус, структуру результатов и соответствие SKU/старых цен запросу.
8. React сохраняет результаты в state и перерисовывает таблицу. `finally` снимает загрузку при любом исходе.

## Алгоритм понятным языком

Откройте `src/pricing.ts`. Переменная `best` сначала равна `Infinity`: это маркер того, что доступная цена ещё не найдена. Все допустимые цены конечны, поэтому настоящая цена не может совпасть с этим маркером.

Цикл проходит по конкурентам. Он сравнивает цену только при `inStock === true`. Конкурент без товара не участвует, даже если его цена меньше остальных. Если новая цена меньше `best`, запоминаем её. Равные минимальные цены не требуют специальной обработки: минимальное значение остаётся тем же.

После цикла создаётся общий объект `original` с неизменёнными SKU и `myPrice`. Если `best` остался `Infinity`, возвращаем `maxPrice` и `NO_COMPETITORS`.

Иначе вычитаем `step` и применяем `Math.floor`. Для iPhone: `384990 - 10 = 384980`. Эта цена лежит между `370000` и `420000`, значит причина — `UNDERCUT`. Более дешёвый конкурент за `379990` отсутствует в наличии и игнорируется.

Если кандидат меньше минимальной границы — возвращаем `minPrice` и `AT_MIN`. Если больше максимальной — `maxPrice` и `AT_MAX`. При **точном совпадении** с любой границей срабатывает последняя ветка, поэтому причина остаётся `UNDERCUT`. Знаки `<` и `>` здесь принципиальны.

`myPrice` нужен для сравнения в интерфейсе, а не для новой цены. Даже если текущая цена уже ниже конкурента, мы не меняем заданный алгоритм.

## Почему Math.floor

Спецификация требует целые тенге и округление вниз: `349999.9 - 0.5 = 349999.4`, результат — `349999`. `Math.round` на другом дробном остатке мог бы округлить вверх. `Math.trunc` отличается для отрицательных чисел: `Math.floor(-0.4) === -1`, а `Math.trunc(-0.4)` даёт отрицательный ноль. После округления кандидат ограничивается допустимым диапазоном.

Не добавляйте «исправление точности» через epsilon: это изменит требуемое поведение JavaScript `Math.floor`. Для реальной финансовой системы точность обсуждают отдельно, но это другое требование.

## Почему функция чистая

Одинаковые входные данные дают одинаковое значение результата. Функция не читает время, сеть, файлы или глобальное состояние, не изменяет товар и возвращает новый объект. Поэтому её можно проверить простым сравнением результата с ожидаемым объектом и использовать в других местах без HTTP-сервера.

Мы не сортируем `competitors`: сортировка могла бы изменить исходный массив и стоит O(n log n). Цикл находит минимум за O(n), используя O(1) дополнительной памяти. Он также избегает ограничения количества аргументов при `Math.min(...largeArray)`.

## Express и валидация

`server/app.ts` создаёт Express-приложение и маршрут. `server/index.ts` открывает порт. Такое разделение позволяет импортировать приложение в тест без запуска постоянного сервера.

`express.json()` превращает JSON-текст в JavaScript-значение, но не проверяет бизнес-структуру. Входное тело имеет тип `unknown`. `server/validation.ts` проверяет объекты, строки, числа, границы и конкурентов, а type guard `value is Product` сообщает TypeScript, что после проверки данные имеют нужную форму.

TypeScript сам не защищает от неверного JSON: его типы стираются при выполнении. Поэтому проверка нужна именно на внешней границе. В `calculatePrice` её нет — функция принимает допустимый `Product`, как гарантирует задание.

Для массива используется `map`: одному входному товару соответствует один результат на той же позиции. Повторяющиеся SKU допустимы. Нельзя заменять эту логику словарём по SKU: это потеряет повторяющиеся записи.

Ошибки пользователя возвращают 400/413/415 с понятным JSON. Непредвиденная ошибка возвращает 500, её детали пишутся в серверную консоль. Middleware ошибок имеет четыре аргумента; Express определяет его по этой сигнатуре.

## React и fetch

`useState` хранит товары, результаты, загрузку, ошибку и время успешного расчёта. Сводка вычисляется из результатов, а не хранится отдельной копией: значения не могут рассинхронизироваться.

`fetch` не бросает исключение для HTTP 400 или 500, поэтому клиент отдельно проверяет `response.ok`. Сетевой сбой попадает в `catch`. `AbortSignal.timeout(15000)` ограничивает время ожидания. Ответ разбирается как `unknown` и проверяется: приведение `as PriceResult[]` само по себе не проверило бы JSON.

Во время загрузки кнопки расчёта, очистки и загрузки демо выключены. Это предотвращает изменение каталога, пока ответ относится к старому набору товаров. При ошибке старые результаты убраны, чтобы они не выглядели как результат последнего запроса. Кнопка «Повторить» отправляет новый запрос.

`ProductTable` отвечает за отображение, `format.ts` — за `Intl.NumberFormat('ru-KZ', { currency: 'KZT' })` и подписи причин. Причина доступна текстом, поэтому цвет не является единственным источником информации. На телефоне широкая таблица прокручивается внутри своего блока.

## Почему архитектура небольшая

У проекта три обязанности: рассчитать цену, передать данные по HTTP, показать их. Для каждой есть отдельные файлы. Здесь не нужны база данных, авторизация, repository pattern, DI-контейнер или очередь: они не решают требования тестового задания и усложнили бы объяснение кода.

Один `package.json` и общий набор типов позволяют установить всё одной командой. Backend работает через `tsx`, frontend собирает Vite. `typecheck` охватывает сервер, React, тесты и конфигурации.

## Что доказывают тесты

- **Алгоритм:** обычная переоценка, отсутствующие конкуренты, выбор минимума и равные цены, ограничения и точные границы, нулевой/дробный шаг, дробные цены, отрицательный кандидат, нулевые/равные границы, независимость от `myPrice`, замороженные данные, детерминированность и 200 000 конкурентов. Во всех случаях сравнивается весь `PriceResult`. Отдельно проверены пять примеров README и весь `expected.json`.
- **API:** правильный результат и порядок, повторяющиеся SKU, пустой массив, не-массивы и повреждённый JSON, типы/числа/границы/конкуренты, отсутствие тела, Content-Type, лимит размера, неподдерживаемая кодировка и неизвестный маршрут. Это настоящие запросы через Supertest.
- **Клиент:** состав POST-запроса, ошибки сети/HTTP/таймаута, не-JSON ответы, неверные результаты и несоответствие отправленным данным. Здесь fetch подменяется контролируемым ответом, чтобы воспроизводить ошибки.
- **Браузерная проверка:** реальный расчёт всех шести товаров, повтор, загрузка, ошибки и восстановление, пустой каталог и мобильная ширина.

100% покрытия относится только к алгоритму: были выполнены все его строки и ветви. Покрытие не доказывает отсутствие любых ошибок; качество зависит от проверенных утверждений и случаев. Скрытые тесты недоступны.

## 15 вероятных вопросов

1. **Почему `calculatePrice` оставлена в `src/pricing.ts`?** Это обязательный внешний контракт автотестов: путь, имя и именованный экспорт менять нельзя.
2. **Какие конкуренты участвуют?** Только с `inStock === true`; цена отсутствующего товара полностью игнорируется.
3. **Что будет без доступных конкурентов?** `maxPrice` и `NO_COMPETITORS`, независимо от текущей цены и шага.
4. **Что будет при точном попадании в `minPrice`?** `UNDERCUT`. Причина `AT_MIN` появляется только при кандидате строго ниже границы.
5. **Зачем округлять после вычитания?** Именно `floor(best - step)` требует спецификация. Округление отдельных операндов может дать другой результат.
6. **Чем floor отличается от round и trunc?** Floor округляет к минус бесконечности, round — к ближайшему целому, trunc отбрасывает дробную часть в направлении нуля.
7. **Влияет ли `myPrice` на новую цену?** Нет, возвращается только в `oldPrice`, без округления или изменения.
8. **Что означает чистая функция?** Нет побочных эффектов и мутаций; значение результата зависит только от входа.
9. **Какова сложность?** O(n) времени для n конкурентов, O(1) дополнительной памяти. Для всего запроса — линейно по общему числу товаров и конкурентов; массив ответов занимает O(m).
10. **Почему нужен runtime-check при TypeScript?** Внешний JSON не обязан соответствовать типам; TypeScript не проверяет входные данные во время выполнения.
11. **Зачем `unknown`, а не `any`?** `unknown` требует сначала проверить значение, а `any` отключает защиту компилятора.
12. **Как различаются 400 и 500?** 400 — неверный запрос пользователя, 500 — непредвиденная ошибка сервера. Превышение лимита — 413, неподдерживаемый формат/кодировка — 415.
13. **Почему fetch требует проверки `response.ok`?** HTTP-ошибка сама по себе не отклоняет Promise fetch; его обычно отклоняет сетевой сбой или прерывание.
14. **Почему здесь не нужен CORS?** Браузер обращается к своему frontend-origin, а Vite пересылает запрос на backend. Для отдельного production-origin потребуется другая конфигурация.
15. **Как проверить проект и что ещё не реализовано?** `npm test`, `npm run typecheck`, `npm run build`, запуск обоих процессов и кнопка расчёта. Демо не подключается к Kaspi и не сохраняет/применяет новые цены.

## Три изменения требований для live coding

### 1. Поиск товаров по SKU или названию

Добавьте состояние `query` и поле поиска в `frontend/App.tsx`. Приведите текст и поля к нижнему регистру. Фильтруйте строки по `includes`.

Сначала соедините каждый товар с его результатом по исходному индексу, затем фильтруйте пары. Если отфильтровать только товары и оставить исходный массив результатов, строки могут получить чужие цены. Удобно поменять props `ProductTable` на массив `{ product, result }`. Пустой результат поиска должен отличаться от пустого каталога. Алгоритм и API не меняются. Проверьте поиск до и после расчёта и одинаковые SKU.

### 2. Общий шаг переоценки для следующего запуска

Добавьте числовое поле в `App.tsx`, допускающее `0` и дробные значения (`min=0`, `step=any`). Храните введённый текст, чтобы временно пустое поле не превращалось в нулевой шаг. После проверки конечного неотрицательного числа создайте новый массив:

```ts
const payload = products.map((product) => ({ ...product, step: customStep }));
const nextResults = await repriceProducts(payload);
```

Не изменяйте `demoProducts` и не считайте цену на клиенте. Типы, серверный контракт и текущая формула уже поддерживают такой шаг. Проверяйте ноль, дробь, пустое/отрицательное значение и большой шаг, который приводит к `AT_MIN`.

### 3. Шаг в процентах вместо фиксированной суммы

Это **новое бизнес-правило**, которого сейчас нет. Добавьте в `src/types.ts` необязательное поле `stepMode?: 'absolute' | 'percent'`, сохранив существующее поведение по умолчанию. Для процентов определите допустимый диапазон по новому требованию, например от 0 до 100.

В `server/validation.ts` проверьте значение режима и диапазон процентного шага. В `calculatePrice` замените только расчёт величины уступки:

```ts
const discount =
  product.stepMode === "percent" ? (best * product.step) / 100 : product.step;
const candidate = Math.floor(best - discount);
```

Фильтрация, отсутствие конкурентов и ограничения остаются прежними. Для `best=1000`, `step=5`, режима percent кандидат равен 950. Добавьте тесты процентов, округления, границ и сохранения старого режима без поля. Название, путь и сигнатура функции остаются совместимыми. В UI понадобится выбор режима и ясная единица шага; правило в блоке объяснения и README нужно обновить.

## Что можно улучшить дальше

Если продукт станет реальным: загрузка собственного каталога, редактирование границ, ограничение числа товаров, история расчётов и экспорт. Для больших каталогов — пагинация/виртуализация и измерение производительности. Для интеграции с магазином — отдельный слой получения конкурентов и применения цен с журналом операций. Для денег — согласованная модель точности. Эти возможности стоит добавлять после уточнения требований.

Перед интервью запустите проект, вручную проверьте минимум, максимум и отсутствие конкурентов, затем объясните каждый файл. Полезнее уверенно понимать текущий короткий алгоритм, чем обещать функции, которых здесь нет.
